# Gozar 1.17.2

## فارسی

- **لاگین دقیقاً مثل نسخهٔ قبل می‌شود:** ترابری مسیر ورود (معامله‌ی نشانهٔ OAuth، رلهٔ Apps Script و حل‌کنندهٔ چالش امنیتی Mozilla/«Client Challenge») عیناً به پیاده‌سازی HttpURLConnection نسخهٔ v1.16.0 برگردانده شد. پیام «Verification complete — Mozilla's security check was not accepted; try again» نتیجهٔ عوض‌شدن کلاینت HTTP (اثرانگشت آن برای لبهٔ Fastly/Mozilla) در ترابری تازه بود؛ حالا همان رفتار ۱.۱۶.۰ بازگشته است — رله، بدون redirect، همان هدرها و همان حل‌کنندهٔ چالش.
- **برنامه‌ها دوباره از تانل رد می‌شوند:** موتور تازه (hev) فقط نشانیِ IP مقصد را از بسته‌های خام می‌شناخت و نام دامنه گم می‌شد؛ مرورگرها از مسیر HTTP proxy با نام واقعی کار می‌کردند ولی برنامه‌ها با مقصد «1.2.3.4:443» به تانل می‌رفتند و سیاست نام‌محور/فهرست مستقیم‌رویی درست جواب نمی‌داد. حالا مقصدهای IPv4 که نامشان از جواب‌های DNS محلی آموخته شده، قبل از اتصال دوباره به نام تبدیل می‌شوند (همان نقشهٔ نام→آدرس ۱.۱۶.۰، این‌بار در resolverِ منتقل‌شده). مقصدهایی که نامی برایشان ثبت نشده مانند قبل با IP وصل می‌شوند.
- **هنوز prerelease است:** مسیر تازهٔ تانل روی دستگاه فیزیکی تأیید نشده؛ قبل از ارتقا به stable این نسخه را روی گوشی امتحان کنید (اتصال + یک برنامهٔ واقعی + ورود).
- اگر بازهم «security check was not accepted» دیدید، رشتهٔ `AUTH failure … (http=… errno=… stage=…)` در لاگ (`adb logcat -s GozarWebView MozillaDiagnostics`) را بفرستید — آن‌وقت دقیقاً معلوم می‌شود کدام درخواست رد شد (معامله‌ی نشانه، موجودی پس، یا حل‌کننده).

## English

- **Sign-in is exactly like the previous version again:** the HTTP transport of the sign-in path (OAuth token exchange, the Apps Script relay, and Mozilla's "Client Challenge" solver) is restored file-for-file to the HttpURLConnection implementation from v1.16.0. "Verification complete — Mozilla's security check was not accepted; try again" was the new client's fingerprint being rejected at the edge; the fix restores the 1.16.0 behavior byte-for-byte — same relay, no redirects, same headers, same challenge solver.
- **Apps tunnel again:** the new native engine (hev) only ever saw raw destination IP addresses — hostnames learned from the local DNS answers were never fed back into the dial path. Browsers worked (the system HTTP proxy carries CONNECT by hostname); raw TUN flows dialled "1.2.3.4:443" and lost direct-routing and hostname-policy matches. IPv4 destinations learned by the local resolver are rewritten to their hostname before connecting — the 1.16.0 name→address behaviour, now carried by the moved DoH resolver. Destinations without a learned name still dial by address, as before.
- **Still a prerelease:** the native tunnel path is not yet validated on a physical device; test this build on-device (Connect + a real app + sign-in) before promoting to stable.
- If "security check was not accepted" still appears, capture `AUTH failure … (http=… errno=… stage=…)` from logcat (`adb logcat -s GozarWebView MozillaDiagnostics`) and send it — that names the exact request that was refused.
