# Gozar 1.18.0

## فارسی

### ۱) علت اصلی «اصلاً تانل نمی‌کند» پیدا و رفع شد (اندروید)

در نسخهٔ ۱.۱۷.x موتور تانل عوض شد: خواندن TUN از استک دستی Kotlin به کتابخانهٔ native
`hev-socks5-tunnel` منتقل شد. همین جابه‌جایی یک خطِ ظاهراً بی‌خطر با خودش آورد:

```kotlin
file.writeText(config)
file.setReadable(false, false)      // ← این خط موتور را می‌کشت
TProxyService.TProxyStartService(file.absolutePath, tunFd)
```

روی اندروید `File.setReadable(false, false)` سه بیتِ خواندن (`S_IRUSR` هم) را پاک می‌کند. کد native
کانفیگش را با `fopen(path, "r")` می‌خواند، شکست می‌خورد، `hev_socks5_tunnel_init` منفی برمی‌گرداند و
موتور بلافاصله خارج می‌شود. چون `TProxyStartService` فقط موفقیتِ ساختِ thread را گزارش می‌کند،
برنامه فکر می‌کرد تانل بالاست: وضعیت «متصل» می‌شد ولی هیچ بایتی از TUN خوانده نمی‌شد. به همین دلیل
هیچ اپی — از جمله تلگرام — تانل نمی‌شد.

**اصلاح:** آن خط حذف شد (فایل توسط `writeText` از اول فقط برای صاحبش خواندنی است)، متن کانفیگ به
`HevConfig` منتقل و اعتبارسنجی شد (mtu/پورت/اعتبارنامه)، و شروعِ موتور حالا اگر thread در همان
لحظه‌های اول از بین برود «شکست» گزارش می‌شود تا UI دیگر «متصل» دروغین نشان ندهد.

**اثبات، نه ادعا:** موتور واقعی را روی یک دستگاه TUN واقعی و یک سرور SOCKS5 ساختگی اجرا کردم
(`tools/hev_config_probe.py`) و هر دو حالت را سنجیدم:

| حالت | بیت خواندن فایل | TCP از TUN | UDP (ASSOCIATE) |
|---|---|---|---|
| کانفیگ خواندنی (اصلاح‌شده) | ✅ | ✅ رفت و برگشت | ✅ رفت و برگشت |
| کانفیگ بدون بیت خواندن (۱.۱۷.x) | ❌ | ❌ موتور قبل از هر بسته خارج شد | ❌ |

### ۲) دسکتاپ: کندی دانلود/آپلود و «تلگرام چیزی دانلود نمی‌کند»

دو علت داشت و هر دو رفع شد:

- **یک نشست H2 برای همهٔ اتصال‌ها.** موتور دسکتاپ حداکثر دو نشست HTTP/2 نگه می‌داشت و هر تعداد
  اتصال را روی همان‌ها سوار می‌کرد. همهٔ streamها یک سوکت TLS مشترک دارند، پس یک سگمنتِ گم‌شده روی
  مسیر دور، کل تانل را متوقف می‌کرد؛ نتیجه: سرعت خیلی پایین و دانلودهایی که شروع نمی‌شوند. حالا هر
  نشست حداکثر ۸ stream می‌گیرد و تا ۸ نشست نگه داشته می‌شود.
- **بودجهٔ timeout و بافرها.** اولین stream هر نشست ۲.۵ ثانیه منتظر handshake کوئیک می‌ماند تا به H2
  برگردد (حالا ۱.۲ ثانیه، و probe بودجهٔ خودش را دارد)؛ بافر کپی رله ۳۲KiB بود که یک جریان پرسرعت را
  عقب می‌انداخت (حالا ۶۴KiB) و MTU دستگاه ۱۶۰۰ است.
- تست تازه: ۱۶ جریان همزمان روی TLS لوکال، و تست بودجهٔ اشتراک نشست.

### ۳) ظاهر: Liquid Glass + Material 3

شیشهٔ واقعی (نه گرادیانِ تزئینی) با کتابخانهٔ `QWEA0/liquidglass` روی این سطوح اضافه شد:

- **کارت اصلی (Hero)** با قطرات و هایلایتِ حساس به حرکت گوشی
- **کارت نمودار مصرف**
- **ردیف انتخاب سرور** در صفحهٔ اصلی
- **شیت لیست سرورها**: خود پنل شیشه‌ای شد و هر ردیف به `LiquidGlassListItem` تبدیل شد، پس لیست دیگر
  «ستون گوشه‌تیز» نیست بلکه یک پنلِ پیوسته با گوشه‌های گرد است
- **نوار پایین**: شیشه‌ای روی پس‌زمینهٔ پنجره
- **توکن‌های شکل**: شعاع‌ها ۱۶/۲۴/۳۲dp، ردیف‌ها و کارت‌ها نیمه‌شفاف (frost) به‌جای سفیدِ تخت، و پس‌زمینهٔ
  پنجره دو نورِ بسیار کم‌رنگ دارد تا عدسیِ شیشه چیزی برای خم‌کردن داشته باشد

محتوا هیچ جابه‌جا نشد: شناسه‌ها، آداپترها و شنوندهٔ کلیک‌ها همان‌ها هستند؛ فقط رسم عوض شد.

**دربارهٔ دستگاه‌های پشتیبانی‌نشده:** هسته‌های native این کتابخانه فقط برای `arm64-v8a` و
`armeabi-v7a` ساخته شده‌اند. روی x86 (شبیه‌ساز) بارگذاری‌شان `UnsatisfiedLinkError` می‌دهد که از نوع
`Error` است و قابل گرفتن نیست. `FoxGlass` یک‌بار تست می‌کند و اگر در دسترس نبود همهٔ فراخوانی‌ها
بی‌اثر می‌شوند؛ آن دستگاه‌ها همان سطوح Material ساده را می‌بینند و کرش نمی‌کنند.

### ۴) آزمایش‌ها

`tools/hev_config_probe.py` (موتور واقعی روی TUN واقعی، در network namespace جدا)، تست‌های واحد
`HevConfigTest`/`FoxGlassTest`، و تست‌های Go برای اشتراک نشست و انتقال پرحجم. CI گیت‌هاب همه را
اجرا می‌کند.

## English

### 1) The reason nothing tunnelled at all (Android)

1.17.x moved TUN handling from the hand-written Kotlin stack to the native
`hev-socks5-tunnel` engine. That move carried one innocuous-looking line:

```kotlin
file.writeText(config)
file.setReadable(false, false)      // <- this killed the engine
TProxyService.TProxyStartService(file.absolutePath, tunFd)
```

On Android `File.setReadable(false, false)` clears all three read bits, owner
included (`UnixFileSystem_md.c: setPermission0`). The native engine opens its
configuration with `fopen(path, "r")`, failed, `hev_socks5_tunnel_init` returned
-1 and the worker exited. `TProxyStartService` only reports that `pthread_create`
succeeded, so the app believed the tunnel was up: the UI said "connected" while
not a single byte was read from the tun device. That is why no app — Telegram
included — was tunnelled.

**Fix:** the chmod is gone (`writeText` already creates the file owner-only), the
document moved into `HevConfig` and is validated (mtu/port/credential), and a
start whose worker dies inside the startup window is now reported as a failure so
the UI can never claim a tunnel it does not have.

**Proven, not asserted:** `tools/hev_config_probe.py` runs the real engine against
a real tun device and a fake SOCKS5 relay in an isolated netns:

| Configuration | owner read bit | TCP through TUN | UDP ASSOCIATE |
|---|---|---|---|
| readable (fixed) | yes | round trip | round trip |
| unreadable (1.17.x) | no | engine exited before any packet | none |

### 2) Desktop: low throughput, and downloads that never start

- **One HTTP/2 session for everything.** The desktop manager kept at most two
  sessions and multiplexed an unbounded number of connections onto them. Every
  stream on a session rides one TLS socket, so a single lost segment on a long
  haul stalled the whole tunnel. Sessions now carry at most 8 streams and up to 8
  sessions are kept.
- **Timeout and buffer budgets.** The first stream of a session paid a 2.5 s QUIC
  handshake timeout before falling back (now 1.2 s, and the probe keeps its own
  budget); relay copies used 32 KiB buffers, which capped a bulk flow (now
  64 KiB) and the tun mtu is 1600.

### 3) Liquid Glass + Material 3 surfaces

Real refraction (not decorative gradients) via `QWEA0/liquidglass` on the hero
card, the traffic chart card, the server row, the server sheet (panel and rows —
so the list is one rounded panel instead of a column of sharp boxes), and the
bottom navigation bar. Shape tokens soften to 16/24/32 dp, rows and cards become
frosted instead of opaque, and the window backdrop gained two very low-contrast
washes so the lens has structure to bend. No content moved: ids, adapters and
click listeners are unchanged.

The library ships native blur kernels for `arm64-v8a` and `armeabi-v7a` only.
Loading them on x86 raises `UnsatisfiedLinkError` from a static initialiser, which
is an `Error` and cannot be caught; `FoxGlass` probes once and becomes a no-op
everywhere it is unavailable, so those devices keep their plain Material surfaces
instead of crashing.

### 4) Verification

`tools/hev_config_probe.py` (real engine, real tun, isolated namespace),
`HevConfigTest`/`FoxGlassTest` unit tests, and Go tests for session sharing and
bulk transfer — all run in GitHub Actions.

### 5) What was not verified automatically

**تست خودکار ورود (Apps Script) برای این نسخه اجرا نشد. این نسخه با تأیید دستی (Manual Approval) به عنوان Stable منتشر شده است.**

The Apps Script account test could not pass unattended. After the fixes below it does reach
Mozilla's sign-in page, fills the address and the password, and observes the real server
response — but Mozilla then asks this account for an emailed sign-in code, and no job in this
repository may read that mailbox. The publish workflow therefore accepts either a successful
automated account run or an explicit `manual_approve` input, and the release body always says
which one applied.

Not covered by the approval: a physical-device run of the sign-in and signup screens, and the
delivery of that sign-in code. Everything else in this release — the tunnel engine, the desktop
core, packaging and signing — is covered by the automated tests listed in section 4.
